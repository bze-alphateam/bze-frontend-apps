# BZE DAO (dao.getbze.com)

Next.js frontend for the BeeZee chain's x/dao module (chain v8.3.0). React 19, Chakra UI v3.

> Commands, env vars, patches, deploy: the **repo root README.md** owns all of that. This file is architecture only.

## Architecture

All shared code comes from `@bze/bze-ui-kit` (the x/dao queries, message builders, validation and tally rules live in `query/dao.ts` and `utils/dao/`). Same shell as staking: an app-specific `AssetsProvider` extends the lib's base `AssetsContextType`, Hive Glow system with the DAO accent (`createHiveGlowSystem('dao')`), shared `AppHeader` with the one nav item "DAOs" (`/`). **There is no DAO creation in this app** (BFE-424): it happens in the Factory (`/dao/new`, ui-kit `CreateDaoFlow`, which stays in ui-kit); `/create` is a plain 404.

## Data

- **Lists come from BZE Scan** (`/api/v1/daos`, `/api/v1/daos/{id}/proposals`, `/api/v1/dao-proposals/{id}`) through the app's own `/api/scan` route (Scan sends no CORS headers for this app). Scan's `type` values are `static_list` / `stake`; proposal statuses are lower-case chain names.
- **Fallbacks**: Scan down → the home list reads the chain's `/bze/dao/daos` (50 per key page, **unfiltered**: no type filter or search, which are hidden, and no open counts) under the amber "Reduced list" notice with a Retry that asks Scan again; "My DAOs" always keeps the administered DAOs from the chain (`daos_by_admin`). Scan's `supported: false`, or the chain's `isDaoModuleSupported()` false while Scan is down, is the one friendly "arrive with v8.3.0" state. A chain network failure is an error, never "not supported".
- **Scan filters of BFE-368** (`member`, `source`, `q`, `pending_admin`): a Scan without them *ignores* the unknown parameters and answers the whole list, so `filtersSupported()` probes once with an invalid `member` address (a newer Scan answers 400, an older one 200). Without them My DAOs lists only the administered DAOs (with a notice) and the name search runs on the loaded page.
- **My DAOs** = administered (chain) ∪ `member` (Scan) ∪ `source` (Scan, the wallet's x/rewards positions as `sr/{reward_id}` / `dr/{staking_denom}`, 20 per request). One row per DAO with every reason ("Admin", "Member", "Staker"); self-owned DAOs are never "Admin".

## The home page (BFE-424)

- **One card, one list**: hero, then a "DAOs" card with the filters (My DAOs switch with a wallet, type All / Member list / Stakers, name search), the notices, the list and the footer. A table from md up, cards below it (both are in the page, a breakpoint shows one; tests and specs use distinct test ids for each). The type's words are "A member list" / "Stakers" (no admin info). No explainer, no open-proposals feed, no logo.
- **URL state** (`lib/home-query.ts`): `?page` (omitted for 1), `?type=static_list|stake`, `?q` (after the 300 ms debounce, never written at mount), `?mine=1` (counts only with a wallet). A page change pushes, a filter change replaces and drops `page`; invalid values are ignored.
- **Paging modes** (`loadDaoPage` returns `mode`): **pages**: Scan with BFE-423 answers `page` + `total` (numbered pager, count line from the rows returned; a page past the end replaces the URL with the last page). **cursor**: a Scan that answers a `page` request without a numeric total (remembered per Scan client, like `filtersSupported()`) and the chain fallback: only Prev / Next over a trail of the visited cursors, "Page n", `?page` ignored. Never `page` together with `cursor` (Scan answers 400). **My DAOs on**: every row of `loadMyDaos` is filtered here (`matchesFilter`) and paged in the browser, 20 per page, count "n of your DAOs"; the all-DAOs list then only runs for page 1 so the node and Scan states still show.
- **Roles** (the You column, the pills on a card) come from `loadMyDaos`, read once per address and matched by DAO id; empty while loading or if it failed.
- **Proxy routes**: `daos` (with `page`), `daos/{id}`, `daos/{id}/history`, `daos/{id}/proposals`, `dao-proposals/{id}` (+ `/votes`), `dao-votes`. The cross-DAO `dao-proposals` list is gone.

## The DAO page

- **Live state is always the chain** (`dao/{id}`, `params`, `dao_controller`, `dao_by_address` to name admin-chain DAOs, bank balances for the treasury, open proposals, the staking reward / Denom Reward of each source, `voting_power`). Scan adds only the creator, labels, the history and the wallet's votes (`dao-votes?voter=`, no DAO filter on Scan's side: pages are read up to a cap and filtered here). A chain miss on the DAO is "not found" (a non-numeric id too, without any request); a Scan miss never is.
- **Failures stay local**: each secondary chain read settles as a `Part` (the panel says it could not be read), each Scan part has a Retry.
- **The shell** (`DaoShell`, DAO UI review 1): every DAO page (`/dao/<id>` and `/dao/<id>/admin`) is the header + the tabs Overview · Proposals `<open>/<total>` · History · Admin console, then the tab's content. The tab lives in the URL (`daoTabHref`, `?tab=` read by `parseDaoTab`, unknown = Overview); on the DAO page a plain click `router.replace`s (no history entry), to or from the admin route it pushes. The Admin console tab (`admin-console-link`) shows only for `consoleRole(dao, wallet) !== 'none'` (admin or pending admin). The counter is Scan's `proposals_open` / `proposals_total` on `GET /daos/{id}` (optional fields: an older Scan has neither), else the chain's open count alone, else no pill.
- **Overview**: Who controls it (Admin cell: No admin / an account / you / a parent DAO, from `describeControl`, Scan's `admin_label` when the chain cannot tell; Voters cell; SubDAOs from `daos_by_admin`, open counts filled in from Scan's `daos?admin=<address>` list (left out when Scan fails), 5 then "Show all"; the governance rules on demand), Who votes, Your voting power, Treasury (two columns on desktop; on a phone: voting power, who controls it, treasury, who votes). No Rules card, no How to join, no Leave, no Free-proposals warning (the Factory shows that at creation). New proposal sits at the top of the Proposals tab.
- **Action buttons** (new proposal, admin console) sit behind `DAO_FEATURES` in `lib/dao-actions.ts`. "Request to join" / "Leave" are only composer shortcut links now (`shortcutHref`); the DAO page shows neither.
- DAO name and description are untrusted: plain text, line breaks kept, links only through `safeHttpUrl` (http/https) in `lib/dao-text.ts`; never HTML.

## The proposal pages (BFE-373)

- **Source of truth**: while the chain has the proposal (`/bze/dao/proposal/{id}`: status, tally, pinned rules, `voting_ended`, `retry_deadline`, `expedite_settleable`) it is the chain; Scan only adds what the chain does not keep (settle height, execution error, deposit release, cleanup) as a retryable part. A chain 404 is the cleanup: the proposal is read from Scan alone and marked **Archived**; both 404 is "not found"; a chain miss with Scan down throws (cannot tell cleaned-up from never-existed). `useProposalPage` polls the chain in place every 60 s while it is voting and the tab is visible; a failed poll keeps what is shown.
- **Bars** come from the pinned config and `pinned_denominator` through ui-kit's tally rules (`lib/proposal-tally.ts`); "met" is never derived from the shown percentages. The share achieved rounds down, the bar it has to reach rounds up, so the text never claims more than the rule.
- **Untrusted text** (title, summary, decoded message fields) is plain text: `PlainText` linkifies http(s) only; the summary is not Markdown here (a deliberate narrowing of the ticket: no new dependency and no HTML path). Unknown messages are shown as raw JSON in a `<pre>`.
- **A config update** is shown against the rules pinned at submission (`before` = the proposal's `pinned_config`), since a diff against the live config is empty once it executed.
- **Lists**: Scan lists one status per request, so Active = `voting` + `execution_failed` merged newest first (chain fallback: both statuses in one request); Finished = the unfiltered newest-first list with the moving and placeholder rows dropped (Scan down: a retry).

## Proposal actions (BFE-374)

- **`lib/proposal-actions.ts` decides, the slot only draws.** `proposalActions({model, wallet, myVote, params, gas, nowMs})` returns which of vote / vote-and-settle / settle (retry, mark expired) / cancel / clean up are offered and enabled, each with its reason. Every unknown input (ballot read failed, eligible weight null, params unreadable, balance still loading) is its own state: it disables with "could not be read", never "no power". "Voting ended" and "settleable" are the chain's flags; the browser clock only picks Retry vs Mark expired (the chain decides by block time) and the stake-DAO early-settle delay.
- **Tally rules are ui-kit's.** Vote and settle = `daoExpediteTally` on the live tally with the wallet's old ballot taken out and its eligible weight added to YES (offered only for an expedited proposal that is not already settleable early, never after a weighted YES, never before a stake DAO's `min_expedite_delay`). The settle outcome is `tallyView(...).passesRegular`.
- **Signing**: `sendDaoTx(tx, msgs)` always passes `daoTxOptions` (direct sign, abort on simulation error) and turns the result into a `TxOutcome`; `unconfirmed` (a confirmation timeout, or a failure after the broadcast with no chain code) means the transaction may still land. `useActionFlow` runs one action at a time and **locks** the actions after an unconfirmed outcome (hash shown; "Check again" re-reads the proposal and, when it shows no change, looks the hash up on the node: landed = sent, failed = "the chain refused it, nothing happened" with the actions open, not found = actions reopen with a "may still land" warning, any other error stays locked) or after a success whose re-read failed.
- **After a transaction** `useProposalPage().refresh()` re-reads the chain in place (`reloadProposalAfterTx`: any chain failure is "failed", only a 404 is "gone" and reloads into the Archived view) and bumps `version`, which re-reads the wallet's ballot/power (`mine`, read once in the page and shared with My vote) and the votes list.
- **Clean-up** repeats `MsgCleanupProposal` (limit 0) until the chain no longer has the proposal (the batch events (`EventProposalCleaned`: `completed`, `processed`) lead, the 404 is the fallback and the confirmation); a batch that cannot be confirmed, a chain that cannot be read, or a batch that is not finished but deleted nothing (`no-progress`) stops the loop, never ends it as done.
- **Fee check**: a wallet with neither a native nor a fee-token balance is blocked with the reason; the simulation judges everything else.
- Ledger: DAO transactions are direct-signed, so the panel carries one faint line saying a Ledger cannot approve them yet (decision of BFE-366, canvas board E7).

## The proposal composer (BFE-375)

- **Registry** (`lib/actions/registry.ts`): an `ActionEntry` is data + pure functions (`available`, `initialFields`, `validate`, `warnings`, `build`); its form is a component under the same id in `components/propose/action-forms.tsx`. **Extension point for BFE-376 / BFE-377: add an entry and a form, nothing else changes** (list, size meter, review, draft and submit are generic). Entries build with the DAO's address from `ctx.dao.address` as signer, so admin-execute can reuse them with the sub-DAO as `ctx.dao`. "Text only" is the empty list, not an entry. All form values are strings so a draft can be stored and checked field by field.
- **Pay** builds `MsgSend` from the DAO; the token is one the treasury holds; amounts are exact BigNumber over the token's exponent, extra decimals are refused, an unknown token is entered in base units; above the treasury's balance is a warning, not an error (execution fails at settle and can be retried).
- **Custom message**: untrusted JSON, parsed with `JSON.parse` only, a type the ui-kit has a codec for (`hasMsgCodec`), read through the codec (`msgValueFromJson`, amino-style JSON: snake_case, enums as numbers, durations as nanoseconds), encoded once, written back from the bytes (`msgValueToJson`) for the preview. Every signer must be the DAO (`signers.ts`), a MsgAdminExecute of the same DAO is refused, anything typed that the read-back does not contain (an unknown or camelCase field, an enum written as a name, a nested typo) is an error (`firstMismatch`), never silently dropped; 100,000 characters at most.
- **Who may propose** (`eligibility.ts`): certain blocks only: no voters (1119), `max_open_proposals` reached (1120), a wallet that is not on a member list / has no stake in a closed DAO (explained with the join text instead of the button). Stake in a source is only a "maybe" (`VotingPower.current` ignores join records): the simulation of `daoTxOptions` surfaces 1118 before anything is signed.
- **Submit** (`hooks/useProposalSubmit.ts`, collaborators injected): `useBZETx().tx` with `daoTxOptions` and `toasts: false`. A confirmation timeout (or any failure after the broadcast without a chain code) is `unconfirmed`: the hash is shown and also kept in `localStorage` (`lib/propose/pending.ts`), so a reload restores the lock; submit stays locked until the node says it landed or was refused (`check`, `getTxLanding`) or the user says it did not land. The new proposal's id comes from the response's events, else from the node's copy of the transaction (`getTxEvents`); `useProposalRedirect` goes to `/proposal/{id}`.
- **Money text** in the composer uses `useCoinFormat().exact` (every digit, never rounded), not `format`.
- **Draft**: `localStorage` `bze-dao:proposal-draft:{daoId}`, version 1, restored field by field (wrong types, unknown actions, oversized fields dropped, an expedited flag or summary the DAO no longer takes dropped), cleared after success; storage that throws loses the draft only.
- The summary preview is plain text (`PlainText`), like the proposal page: no Markdown renderer (deliberate narrowing of the ticket, as in BFE-373).
- `describeBuilt` (`lib/propose/describe.ts`) reads a built message back through the codec and hands it to BFE-373's describers (`asRest` turns the codec's ratios/durations/enums of a `config` back into the chain's REST form). A new entry whose message the describers do not know shows as raw JSON until a describer is added there.

## DAO self-management actions (BFE-376)

- **Entries** in the registry: `update-metadata` (rename), `update-rules` (whole config; a setting nobody touched is sent exactly as the DAO has it, because the form rounds), `update-members` (member lists), `update-electorate` (stake DAOs; the lock minimum is checked for added sources only, a self-owned DAO needs voting stake without its own), `nominate-admin` / `withdraw-nomination` (self-owned DAOs only: the chain wants the current admin as signer), `accept-nomination` (nominations Scan finds, confirmed on the chain), `sub-dao-admin` and `sub-dao-execute` (DAOs this DAO administers; the inner actions come from the same registry with the sub-DAO as `ctx.dao` through `subContext`).
- **Relations** (`lib/propose/relations.ts`): sub-DAOs (with treasuries), incoming nominations and the staking sources are read before the composer opens, each `null` when unreadable (never "none"); only the nominations may be skipped when Scan is down. `ActionContext` carries them, `available(dao, ctx)` reads them.
- **Admin execute** refuses `authz.MsgGrant`, `feegrant.MsgGrantAllowance` and `authz.MsgExec` (1133) and never a settle message; `msgValueToJson` (ui-kit) reads the messages an admin execute packs, so the review shows every inner message.
- **Shortcuts**: "Request to join" / "Leave" link to `/dao/{id}/propose?shortcut=join|leave`; the composer fills the connected wallet's address (never one from the link) unless an unsent draft exists, then drops the query.

## The admin console (BFE-377)

- **One gate**: `lib/admin/access.ts` `consoleRole(dao, wallet)` is `admin` (the external admin of a DAO that is not self-owned), `nominee` (the account in `pending_admin`) or `none`. The DAO page's "Admin console" link (`DAO_FEATURES.adminConsole`) and the page itself read it from the chain's DAO record; the route carries only the DAO number, never an address or a role. A self-owned DAO has no console: its voters act through proposals.
- **Run actions as the DAO** reuses the composer's registry: the actions come from `ACTION_ENTRIES` with the DAO as `ctx.dao` (`useActionContext(view, relations, true)`, `runsNow`: a payment the treasury cannot cover is an error here, a warning in a proposal), composed by `composeAdminActions` in `lib/actions/sub-dao.ts`, the same function the sub-DAO execute entry uses (`levelsAbove` 1 there, 0 here). It applies the chain's rules for this path: the entry must be offered for the DAO, no settle and no authz grant / fee allowance / authz exec (1133, `ADMIN_REFUSED_TYPES`), 1 to `max_msgs_per_proposal` messages within `max_proposal_bytes`, and `inspectExecution` (`lib/actions/execution.ts`) reads every message as the chain will (nested admin executes included) to refuse the same types at any depth and to count the nested executions (at most 5, 1134). The review shows the outer `MsgAdminExecute` (wallet as signer, DAO, size) and every inner and nested message through the proposal describers (`ActionsPanel` with its `wording` / `expanded` props); nothing is sent while a message cannot be read back.
- **Nominate / withdraw / hand over** are direct wallet messages (`MsgNominateAdmin`, `MsgWithdrawAdminNomination`, `authority` = the wallet, the chain wants the current admin, 1109), not registry entries. `lib/admin/operations.ts` holds the checks: one nomination at a time (1112), which the chain looks at **before** the empty nominee, so a pending nomination also blocks the handover to voters; the nominee rules through `nomineeProblem` (`lib/actions/admin.ts`, shared with the entries); the live electorate through `handOverProblem` (`lib/actions/electorate.ts`, shared with the sub-DAO entry): stake without the DAO's own, and unreadable sources block it, never "no voters". The handover needs the phrase typed first.
- **Accept** (`lib/admin/nomination.ts`, DAO UI review 1): `isNominationStale(chain, dao)` works out the chain's 1135 the way `checkNominationControl` does: it walks `dao_controller`'s `path` from the DAO's admin upward and the nomination is stale when a DAO on it has an `admin_seq` above `pending_admin_seq` (BigInt compare). The DAO itself is skipped (its own admin change clears the nomination), so only a DAO run by another DAO can go stale. It never throws: `{stale: true, parent, changed}` (`parent` = the DAO's admin, the one that has to nominate again) or `{stale: false, checked}` (`checked` false when a read failed). The composer reuses it. The nominee sees one card: stale → the stale card (title, Stale pill, who has to nominate again, View DAO); otherwise, an unchecked result included, the accept card (title, Nominated pill, the responsibility tick, View DAO, Accept and become admin disabled until ticked). Stale with the change further up than the parent, the card names that DAO ("<Changed>, which controls <Parent>, …"). The admin view has no side panel. On the admin route the shell's tabs follow the last connected wallet (`flowWallet`), so after a disconnect the Admin console tab stays and the console asks to connect the wallet again.
- **One flow** (`hooks/useAdminFlow.ts`): `useActionFlow` (ActionKind widened with `admin-execute`, `nominate`, `withdraw`, `hand-over`, `accept`) with `sendDaoTx` and `daoTxOptions`. An unconfirmed transaction (a timeout) locks every operation, its hash is kept per DAO and wallet in `localStorage` from the moment it is broadcast (`lib/admin/pending.ts`), a reload restores the lock, and "Check again" asks the node (`getTxLanding`). An admin execute is judged by its hash alone (a payment changes nothing the DAO record shows); the others also by `controlFingerprint`. After a transaction the DAO is re-read and the wallet goes back to the DAO page.
- **My DAOs "Nominated"**: Scan `daos?pending_admin=<wallet>` (only when `filtersSupported()` is `yes`: an older Scan ignores the parameter and answers every DAO), every page, each candidate confirmed by the chain's own `pending_admin`; a list that does not end, or a failed read, is the `nominatedFailed` notice, never a short list.
